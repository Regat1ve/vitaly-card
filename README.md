# Цифровая визитка — Виталий Зеленов

Тестовое задание: визитка специалиста на **Git, TypeScript, Node.js, NestJS, Prisma, GraphQL, Docker**
и с Claude Code как рабочим инструментом.

Визитка — не набор HTML-файлов, а сервис: данные лежат в PostgreSQL, наружу смотрит GraphQL API,
а страница, которую видит человек, — обычный клиент этого же API. Одна модель данных, один источник
правды, никакого дублирования содержимого в разметке.

- **Живая визитка:** ссылка в чате hh
- **Схема и песочница GraphQL:** `/graphql`
- **Состояние сервиса и базы:** `/health`

## Запуск

### Через Docker — одна команда

```bash
docker compose up --build
```

Поднимет PostgreSQL, накатит схему Prisma, наполнит визитку и запустит API на http://localhost:3000.

### Без Docker

```bash
cp .env.example .env      # и подставить свою строку подключения к PostgreSQL
npm install
npm run prisma:push       # создать таблицы
npm run seed              # наполнить визитку
npm run start:dev         # http://localhost:3000
```

## Проверки

```bash
npm test          # юнит-тесты сервиса
npx tsc --noEmit  # типы
```

CI (`.github/workflows/ci.yml`) делает больше, чем запускает тесты: он **собирает образ, поднимает
контейнер вместе с PostgreSQL и бьёт в живой GraphQL настоящими запросами** — валидным и заведомо
невалидным. Зелёный CI означает, что Dockerfile и compose действительно работают, а не просто
написаны.

## Что можно спросить у API

```graphql
# вся визитка одним запросом
{
  profile {
    fullName headline summary location timezone email phone
    links { kind label url }
    skills { name category level years }
    projects { name role year stack highlights url repoUrl }
  }
}

# проекты, где есть конкретная технология — фильтрация в PostgreSQL, не в Node
{ projects(stack: "PostgreSQL") { name year stack } }

# навыки по категории
{ skills(category: BACKEND) { name level } }

# написать владельцу — мутация пишет в базу, а не возвращает заглушку
mutation {
  contact(input: {
    name: "Мария Леви"
    email: "hr@example.com"
    message: "Здравствуйте! Посмотрели визитку, давайте созвонимся."
  }) { id createdAt }
}
```

Невалидный ввод возвращает ошибку с перечнем полей, а не «Bad Request Exception»:

```json
{
  "errors": [{
    "message": "Имя — от 2 до 80 символов. Нужен корректный адрес почты.",
    "extensions": { "code": "BAD_REQUEST", "fields": ["Имя — от 2 до 80 символов.", "..."] }
  }]
}
```

## Решения и почему так

**GraphQL по code-first.** Схема генерируется из типов TypeScript, а не пишется отдельным SDL-файлом.
Источник один, поэтому схема и код не могут разойтись; `schema.gql` не хранится в репозитории —
это производная, а держать в git копию, которая рано или поздно устареет, незачем.

**Связи резолвятся по требованию.** Запрос `{ profile { fullName } }` не трогает таблицы ссылок,
навыков и проектов. Профиль здесь ровно один, поэтому N+1 не возникает; появись список профилей —
понадобился бы DataLoader, и это первое, что я бы добавил.

**Фильтр по стеку живёт в базе.** `stack: { has: "PostgreSQL" }` превращается в операцию над массивом
в PostgreSQL. Тянуть все проекты и отсеивать лишние в Node — привычка, которая незаметна на пяти
записях и больно бьёт на пяти тысячах.

**Мутация действительно пишет.** `contact` сохраняет обращение в таблицу с валидацией через
class-validator. Мутация, возвращающая заглушку, ничего не доказывает.

**Ограничение частоты.** Визитка публичная, а мутация пишет в базу — без ThrottlerGuard её зальют
мусором за вечер. Штатный гард не понимает контекст GraphQL, поэтому в `GqlThrottlerGuard` переопределён
разбор запроса.

**Health-check дёргает базу.** Ответ «ok» от процесса, который не видит PostgreSQL, — бесполезная
зелёная лампочка. Тот же эндпоинт использует HEALTHCHECK в Dockerfile.

**Контейнер не под root.** Отдельный пользователь `app`, многостадийная сборка, в финальном образе
нет ни исходников на TypeScript, ни devDependencies.

**Уровни навыков — три ступени, а не проценты.** «85 % владения React» не значит ничего, а
«пишу каждый день» / «писал в проде» / «пробовал в проекте» — значат. NestJS и GraphQL стоят
на LEARNING честно: этот проект и есть мой первый на них.

## Про Claude Code

Он в списке технологий задания, и я работаю с ним каждый день — но как с инструментом под контролем,
а не как с генератором «лишь бы собралось». Что это значит на практике, видно прямо в этом репозитории:

- **план до кода**: модель данных и контракт GraphQL продуманы раньше, чем появился первый резолвер;
- **узкие диффы и осмысленная история коммитов** — не «первый коммит» на весь проект;
- **комментарии объясняют решения, а не синтаксис**: почему связи ленивые, почему prisma лежит
  в dependencies, почему throttler пришлось переопределить;
- **проверки на нетривиальных местах**: юнит-тесты на сервис и CI, который реально поднимает контейнер;
- **где я с ассистентом не согласился** — самое интересное на разборе, и такие места здесь есть.

Свод практик держу публично: [github.com/Regat1ve/claude-code-playbook](https://github.com/Regat1ve/claude-code-playbook)

## Что осознанно не сделано

- **Миграций Prisma нет**, схема накатывается через `db push`. Для визитки с одной схемой этого
  достаточно; для продукта с историей изменений нужна папка `migrations` и `migrate deploy`.
- **Аутентификации нет** — визитка публична по назначению. Обращения из формы пишутся, но читать их
  через API нельзя: запроса `contactRequests` в схеме нет намеренно, иначе почты писавших были бы
  доступны всем.
- **Подписок GraphQL нет** — обновлять визитку в реальном времени некому.
- **DataLoader не подключён** — при одном профиле он был бы преждевременной оптимизацией.
